# RM-RELEASE requirements

| ID | Requirement | Verification |
|---|---|---|
| `RM-RELEASE-R001` | **Dependency-ordered fleet release planning.** A maintainer can release a selected set of repositories in an order derived from declared and observed dependency edges, producing a census of each repository's package, version source, and dependency group and rejecting cycles before any mutation. | A fixture with an omitted repository, contradictory metadata, or a dependency cycle yields an incomplete receipt or a typed diagnostic rather than an executable plan. |
| `RM-RELEASE-R002` | **Complete per-repository dependency census.** The census records each selected repository's package identity, version source, dependency group, and production source observations across Python, Rust, and JavaScript/TypeScript, making any missing or contradictory metadata explicit, and derives expected agent identities from the canonical repository manifest, rejecting any identity drift before generating documentation. | A fixture that omits a repository or a source yields an incomplete receipt and no executable release plan. |
| `RM-RELEASE-R003` | **Acyclic, typed dependency graph per release scope.** The planner builds a directed dependency graph with edges classified as runtime, build, development, optional, deployment, or frontend, and rejects any cycle within a declared release scope rather than silently dropping an edge to force acyclicity. | A two-node cycle and a cross-phase upward edge each produce a stable, typed diagnostic in a fixture test. |
| `RM-RELEASE-R004` | **Immutable, content-addressed release plan digest.** The release plan binds the selected repository identities, their source revisions, the manifest and census digests, the dependency-edge evidence, the stage order, and any version-floor rewrite into one immutable plan digest. | Reordering the input data leaves the digest unchanged, while changing a relevant source revision changes it. |
| `RM-RELEASE-R005` | **Dependency-ordered execution with trusted gating.** Setup, install, validation, build, publication, and downstream-readiness steps execute in dependency order, and no stage mutates a repository unless it holds a complete, current plan and trusted publication evidence from its predecessors. Downstream readiness follows the pipelines wheel rule (`PIPE-RELEASE-R008`). A dependency version is available when it has a wheel compatible with the target interpreter or platform. A missing sdist on that version is the advisory `sdist_missing`, not a failure. A version with only an sdist, or with no compatible wheel, fails unless the consumer lists the package in `[tool.pipelines] allow-source-build`. `partial_publish` applies only while the forge reports that version's release run as in progress. | A missing artifact, a failed check, or a stale predecessor stage blocks its dependents before they can mutate anything, as shown by a fixture test. `tests/test_dependency_readiness.py` shows that a wheel without an sdist passes with the advisory, an sdist-only version fails, an allow-listed sdist-only version passes, an in-progress run reports `partial_publish`, and a concluded run with a wheel passes. |
| `RM-RELEASE-R006` | **One shared admission contract across release routes.** The Git, CLI, and MCP release routes all share the same admission and executor contract, and a failed activation leaves the prior route fully in place with no partially switched entry point. | Each route produces the identical stage outcome and refusal result when run against the same shared fixture. |
| `RM-RELEASE-R007` | **Per-stage receipts with retry and rollback evidence.** Each release stage records the exact artifact and repository identity it acted on, its outcome, a retry key, and the rollback or repair action available for it. | Injecting a push failure produces a reconciliable partial-state record and never a false success report. |
| `RM-RELEASE-R008` | **Publish this package only from version tags.** Repository Manager invokes the shared Python publication workflow only for pushed v-prefixed tags, requires its tag admission check, and retains its exact-source/conflicting-tag and secret checks unchanged. Ordinary main pushes and pull requests run source CI without publishing. | tests/test_package_publication_workflow.py verifies tag/branch routing, shared admission delegation, and unchanged secret wiring. |
| `RM-RELEASE-R009` | **Deterministic, resumable dependency-floor rollout through PRs.** `repository-manager rollout --dependency D --floor X` (MCP `rm_rollout`, actions plan/apply/status/release; one shared core `rollout.run_rollout_action`) selects the workspace.yml group (selector or subdirectory prefix, default `agent-connectors`) intersected with the forge's non-archived repositories and with repositories whose default-branch `pyproject.toml` declares D. It plans each repository from the forge (current floor, version, any rollout PR) into an append-only JSONL ledger under XDG state keyed by (dependency, floor, repo). Apply, in a fresh `git worktree add` off `origin/<default>` with bounded parallelism, sets `>=X,<next-minor`, runs `uv lock --upgrade-package D --refresh` and fails the row unless the lock resolves D ≥ X, patch-bumps through the bumpversion config and Dockerfile pins, adds a CHANGELOG entry, regenerates `specs/*/status.json` with `pipelines-hook spec-status --write`, runs pre-commit, commits an explicit file list with the repository's configured identity (never `claude`), pushes, opens a PR and arms `gh pr merge --auto --rebase`. It never pushes to main, never stashes and never uses `git add -A`. A re-run resumes: an open or merged rollout PR or an already-pushed branch is adopted, never duplicated or re-bumped. `status` reports merged, failing with failing check names, or pending. `release` tags `v<version>` on main's HEAD only after the PR merged and main's floor is ≥ X, skipping existing tags; it is safe on a schedule. This replaces the retired phased bump/push, which pushed to main, named pre-rename packages and never raised a floor or relocked. | `tests/test_rollout.py` with fake git/gh/uv runners and no network: resume idempotency, a lock below the floor fails the row, an existing open PR is adopted with no duplicate, a pushed branch reopens without re-bump, spec-status regen is staged in the PR, status names failing checks, tags only after merge and floor met, existing tags skipped, `claude` identity refused. After the patch bump the apply step re-runs `uv lock` (no upgrade) so `uv.lock` records the package's new own version, then runs the repository's full pre-commit (also the relocated `.config/pre-commit.yaml`, via `uvx` when absent) and stages every hook-rewritten file by explicit path. The default runtime manifest is `~/.config/arbora/workspace.yml` (`ARBORA_CONFIG_DIR` overrides), with no fallback to a former location. |
