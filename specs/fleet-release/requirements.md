# RM-RELEASE requirements

| ID | Requirement | Verification |
|---|---|---|
| `RM-RELEASE-R001` | **Dependency-ordered fleet release planning.** A maintainer can release a selected set of repositories in an order derived from declared and observed dependency edges, producing a census of each repository's package, version source and dependency group and rejecting cycles before any mutation. Caller chain: the release planner is a library path with no CLI or MCP verb: `capture_complete_manifest_census` (`repository_manager/development/fleet_manifest.py:418`) builds the census, `build_dependency_graph` (`repository_manager/development/workspace_release.py:1967`) builds the graph, `build_frozen_release_plan` (`repository_manager/development/workspace_release_plan.py:4513`) freezes the plan, and `ReadOnlyFleetEvidenceProvider` (`repository_manager/development/fleet_evidence_provider.py:33`) calls `prepare_fleet_release` (`repository_manager/development/fleet_release_gate.py:250`), which refuses while `FLEET_RELEASE_ACTIVATION` (:31) is not `open`. Shape: the types are `DependencyGraph` and `WorkspaceReleasePlan` (`workspace_release.py:1070`, :721) and `FrozenReleasePlan`; one planner exists and no second ordering is added. Depends: `RM-RELEASE-R002`, `RM-RELEASE-R003`, `RM-RELEASE-R004`. | Test: `tests/test_fleet_release_gate.py::test_incomplete_census_refuses_before_any_live_release_authority` and `tests/test_fleet_evidence_provider.py::test_current_manifest_without_verified_metadata_refuses`. |
| `RM-RELEASE-R002` | **Complete per-repository dependency census.** The census records each selected repository's package identity, version source, dependency group and production source observations across Python, Rust and JavaScript/TypeScript, makes any missing or contradictory metadata explicit, and derives expected agent identities from the canonical repository manifest, rejecting identity drift before generating documentation. Caller chain: `capture_census` (`repository_manager/development/fleet_census.py:551`) reads each source through `_read_source` (:114) and returns a `CensusReceipt` (:79) whose `complete` flag stays false without an independent proof from `capture_source_universe` (`repository_manager/development/fleet_source_universe.py:162`); the documentation-readiness action reaches the manifest identities through `repository_manager/docs_readiness.py` from the CLI `run_docs_readiness_cli` and the MCP docs-readiness tool. Shape: one `EdgeObservation` per observed edge with its dependency class; the independent Git-tree proof is `verify_source_universe` (:200); identity drift is refused before the generator runs. Depends: none. | Test: `tests/test_fleet_census.py::test_bounded_census_captures_four_evidence_families`, `tests/test_fleet_source_universe.py::test_extra_tracked_source_refuses_manifest_self_attestation` and `tests/test_docs_readiness_fleet_action.py::test_manifest_selection_drift_fails_closed_before_generator`. |
| `RM-RELEASE-R003` | **Acyclic, typed dependency graph per release scope.** The planner builds a directed dependency graph with edges classified as runtime, build, development, optional, deployment or frontend, and rejects any cycle within a declared release scope rather than silently dropping an edge to force acyclicity. Caller chain: `build_dependency_graph` (`repository_manager/development/workspace_release.py:1967`) runs `_topological_groups` (:2107) and raises through `_cycle_diagnostic` (:2077) before it returns a graph; the fleet order raises `FleetCycleError` (:2366) from `build_fleet_order_receipt` (:2605); the per-repository phase direction is checked by `check_phase_direction` (`repository_manager/dependency_readiness.py:2016`). Shape: the diagnostics are typed `Diagnostic` values (`workspace_release.py:73`) with a `GraphDiagnosticCode` (:54); no edge is dropped to reach acyclicity. Depends: `RM-RELEASE-R002`. | Test: `tests/test_workspace_release_dag.py::test_cycle_refuses_before_a_graph_is_returned`, `tests/test_fleet_order_receipt.py::test_fleet_scc_census_reports_each_exact_component` and `tests/test_phase_direction.py::test_phase4_runtime_dependency_on_phase5_package_fails`. |
| `RM-RELEASE-R004` | **Immutable, content-addressed release plan digest.** The release plan binds the selected repository identities, their source revisions, the manifest and census digests, the dependency-edge evidence, the stage order and any version-floor rewrite into one immutable plan digest. Caller chain: `build_frozen_release_plan` (`repository_manager/development/workspace_release_plan.py:4513`) builds the plan and `plan_digest` (`repository_manager/development/workspace_release.py:1381`) computes the digest; `bind_fleet_release_plan` (`workspace_release_plan.py:4600`) is called by `prepare_fleet_release` (`fleet_release_gate.py:250`) to bind the fleet order to the plan. Shape: canonical payloads are sorted before hashing through `_canonical_json` (`workspace_release.py:1377`) and one digest serializer serves every route; a stale or tampered plan is rejected on reconstruction. Depends: none. | Test: `tests/test_workspace_release_plan.py::test_plan_digest_and_stages_are_independent_of_input_order`, `tests/test_workspace_release_plan.py::test_profile_source_and_consent_changes_change_exact_digest` and `tests/test_fleet_order_receipt.py::test_fleet_plan_binding_rejects_stale_or_tampered_order`. |
| `RM-RELEASE-R005` | **Dependency-ordered execution with trusted gating.** Setup, install, validation, build, publication and downstream-readiness steps execute in dependency order, and no stage mutates a repository unless it holds a complete, current plan and trusted publication evidence from its predecessors. Downstream readiness follows the pipelines wheel rule (`PIPE-RELEASE-R008`): a dependency version is available when it has a wheel compatible with the target interpreter or platform; a missing sdist on that version is the advisory `sdist_missing`, not a failure; a version with only an sdist, or with no compatible wheel, fails unless the consumer lists the package in `[tool.pipelines] allow-source-build`; `partial_publish` applies only while the forge reports that version's release run as in progress. Caller chain: the `dependency-readiness` hook of `.pre-commit-config.yaml` and the release barrier call `check_constraint` (`repository_manager/dependency_readiness.py:2523`), which applies `_WheelRule` (:2247) and asks `forge_release_run_probe` (:2721) for a run in progress; stage permits come from `authorize_fleet_stage` (`repository_manager/development/fleet_release_gate.py:300`). Shape: the staged executor that runs each stage is not built; the permit and the readiness check are the built gates. Depends: `RM-RELEASE-R004`. | Test: `tests/test_dependency_readiness.py::test_wheel_without_sdist_passes_with_the_sdist_missing_advisory`, `tests/test_dependency_readiness.py::test_sdist_only_version_fails`, `tests/test_dependency_readiness.py::test_sdist_only_version_on_the_allow_list_passes`, `tests/test_dependency_readiness.py::test_in_progress_release_run_reports_partial_publish` and `tests/test_dependency_readiness.py::test_concluded_run_with_a_wheel_passes_without_asking_the_forge`. The stage-blocking proof `tests/test_fleet_release_gate.py::test_stale_predecessor_blocks_dependent_stage` is planned. |
| `RM-RELEASE-R006` | **One shared admission contract across release routes.** The Git, CLI and MCP release routes all share the same admission and executor contract, and a failed activation leaves the prior route fully in place with no partially switched entry point. Caller chain: every legacy route calls `require_legacy_release_route` (`repository_manager/development/fleet_release_gate.py:38`) before an effect: the setup route (`repository_manager/repository_manager.py:865`), the install route (:1832), `Git.push_project`, the MCP workspace tool (`repository_manager/mcp_tools/workspace.py:48`) and the MCP projects tool (`repository_manager/mcp_tools/projects.py:22`); the CLI reaches the same `Git` methods. Shape: while activation is `closed_pending_source_universe_proof` the legacy selection is preserved; once open, the legacy route raises `FleetReleaseGateError` before creating a job and only a stage permit executes. The route registry switch itself is not built. | Test: `tests/test_fleet_release_gate.py::test_open_cutover_refuses_legacy_git_routes_before_effect` and `tests/test_fleet_release_gate.py::test_closed_cutover_preserves_legacy_route_selection`. |
| `RM-RELEASE-R007` | **Per-stage receipts with retry and rollback evidence.** Each release stage records the exact artifact and repository identity it acted on, its outcome, a retry key and the rollback or repair action available for it. Caller chain: the durable job service `RepositoryJobService` (`repository_manager/development/jobs.py:1384`) records each job's identity and outcome, `retry` derives the key `retry:<job_id>:<attempt>` (:1248) and `reconcile` (:1711) proposes an idempotent repair with the key `repair:<digest>` (:1749). Shape: the retry key, the repair proposal and the reconciliation classes exist for repository jobs; a release-stage receipt type that carries the artifact digest and the rollback action is not built, and injected push failures are covered through the job path. Depends: `RM-RELEASE-R005`. | Test: `tests/test_repository_job_service.py::test_reconcile_enqueues_idempotent_follow_up_without_inline_mutation`, `tests/test_repository_job_service.py::test_retry_chain_consumes_the_original_budget_without_replenishing_it` and `tests/test_durable_build_broker.py::test_worker_surfaces_release_reconciliation_without_rerunning`. |
| `RM-RELEASE-R008` | **Publish this package only from version tags.** Repository Manager invokes the shared Python publication workflow only for pushed v-prefixed tags, requires its tag admission check, and retains its exact-source and conflicting-tag and secret checks unchanged. Ordinary main pushes and pull requests run source CI without publishing. Caller chain: a push event on GitHub runs `.github/workflows/connector.yml`, whose `pipeline` job delegates to the shared connector pipeline; the tag filter `v*` selects publication and the branch filter `main` selects source CI. Shape: `connector.yml` is the only source CI caller besides `windows-ci.yml`; the secrets wiring is left unchanged. Release tags are created by the bumper and the owner, and existing tags stay immutable. | Test: `tests/test_package_publication_workflow.py::test_source_ci_still_validates_main_and_pull_requests` and `tests/test_package_publication_workflow.py::test_connector_workflow_is_the_only_source_ci_caller`. |
| `RM-RELEASE-R009` | **Deterministic, resumable dependency-floor rollout through PRs.** `repository-manager rollout --dependency D --floor X` (MCP `rm_rollout`, actions plan, apply, status and release; one shared core `rollout.run_rollout_action`) selects the workspace manifest group (selector or subdirectory prefix, default `agent-connectors`) intersected with the forge's non-archived repositories and with repositories whose default-branch `pyproject.toml` declares D. It plans each repository from the forge into an append-only JSONL ledger under the XDG state directory keyed by (dependency, floor, repository). Apply, in a fresh `git worktree add` off `origin/<default>` with bounded parallelism, sets `>=X,<next-minor`, runs `uv lock --upgrade-package D --refresh` and fails the row unless the lock resolves D at X or above, patch-bumps through the bumpversion config and Dockerfile pins, adds a CHANGELOG entry, regenerates `specs/*/status.json` with `pipelines-hook spec-status --write`, runs pre-commit, commits an explicit file list with the repository's configured identity (never a coding-agent identity), pushes, opens a PR and arms `gh pr merge --auto --rebase`. It never pushes to main, never stashes and never uses `git add -A`. A re-run resumes: an open or merged rollout PR or an already-pushed branch is adopted, never duplicated or re-bumped. `status` reports merged, failing with failing check names, or pending. `release` tags `v<version>` on main's HEAD only after the PR merged and main's floor is at X or above, skipping existing tags. Caller chain: the console script `repository-manager` dispatches `rollout` at `repository_manager/cli_commands/parser.py:46` to `run_rollout_cli` (`repository_manager/cli_commands/rollout.py:57`); the MCP tool `rm_rollout` (`repository_manager/mcp_tools/rollout.py:23`) calls the same `run_rollout_action` (`repository_manager/rollout.py:962`), which drives `Rollout.plan` (:554), `apply` (:578), `status` (:842) and `release` (:877). Shape: all process calls go through the injectable `Runner` protocol (:72) with `subprocess_runner` (:82) as the default, so the fakes of the tests replace git, gh, uv and pre-commit; the ledger is `Ledger` (:317); the default runtime manifest is the arbora runtime copy, with no fallback to a former location. After the patch bump the apply step re-runs `uv lock` without upgrade so `uv.lock` records the package's new own version, runs the repository's full pre-commit (also the relocated `.config/pre-commit.yaml`, through `uvx` when absent) and stages every hook-rewritten file by explicit path. | Test: `tests/test_rollout.py::test_apply_opens_one_pr_with_bump_changelog_and_status_regen`, `tests/test_rollout.py::test_resume_is_idempotent_no_duplicate_pr_or_double_bump`, `tests/test_rollout.py::test_lock_that_misses_the_floor_fails_the_row`, `tests/test_rollout.py::test_release_tags_only_after_merge_and_floor_met`, `tests/test_rollout.py::test_refuses_claude_identity` and `tests/test_rollout.py::test_default_manifest_path_is_arbora`. |
