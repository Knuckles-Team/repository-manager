# RM-RELEASE-001 requirements

Every requirement this specification owns, with the proof that closes it. Delivery state and
public evidence for each ID are recorded in [`status.json`](status.json); this file defines what
each ID means. The design is in [`spec.md`](spec.md) and [`plan.md`](plan.md), the test contract
in [`test-spec.md`](test-spec.md), and the work order in [`tasks.md`](tasks.md).

| ID | Requirement | Verification |
|---|---|---|
| `RM-RELEASE-R001` | **Dependency-ordered fleet release planning.** A maintainer can release a selected set of repositories in an order derived from declared and observed dependency edges, producing a census of each repository's package, version source, and dependency group and rejecting cycles before any mutation. | A fixture with an omitted repository, contradictory metadata, or a dependency cycle yields an incomplete receipt or a typed diagnostic rather than an executable plan. |
| `RM-RELEASE-01` | **Complete per-repository dependency census.** The census records each selected repository's package identity, version source, dependency group, and production source observations across Python, Rust, and JavaScript/TypeScript, making any missing or contradictory metadata explicit, and derives expected agent identities from the canonical repository manifest, rejecting any identity drift before generating documentation. | A fixture that omits a repository or a source yields an incomplete receipt and no executable release plan. |
| `RM-RELEASE-02` | **Acyclic, typed dependency graph per release scope.** The planner builds a directed dependency graph with edges classified as runtime, build, development, optional, deployment, or frontend, and rejects any cycle within a declared release scope rather than silently dropping an edge to force acyclicity. | A two-node cycle and a cross-phase upward edge each produce a stable, typed diagnostic in a fixture test. |
| `RM-RELEASE-03` | **Immutable, content-addressed release plan digest.** The release plan binds the selected repository identities, their source revisions, the manifest and census digests, the dependency-edge evidence, the stage order, and any version-floor rewrite into one immutable plan digest. | Reordering the input data leaves the digest unchanged, while changing a relevant source revision changes it. |
| `RM-RELEASE-04` | **Dependency-ordered execution with trusted gating.** Setup, install, validation, build, publication, and downstream-readiness steps execute in dependency order, and no stage mutates a repository unless it holds a complete, current plan and trusted publication evidence from its predecessors. | A missing artifact, a failed check, or a stale predecessor stage blocks its dependents before they can mutate anything, as shown by a fixture test. |
| `RM-RELEASE-05` | **One shared admission contract across release routes.** The Git, CLI, and MCP release routes all share the same admission and executor contract, and a failed activation leaves the prior route fully in place with no partially switched entry point. | Each route produces the identical stage outcome and refusal result when run against the same shared fixture. |
| `RM-RELEASE-06` | **Per-stage receipts with retry and rollback evidence.** Each release stage records the exact artifact and repository identity it acted on, its outcome, a retry key, and the rollback or repair action available for it. | Injecting a push failure produces a reconciliable partial-state record and never a false success report. |
