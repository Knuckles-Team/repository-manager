# RM-MATERIALIZE requirements

| ID | Requirement | Verification |
|---|---|---|
| `RM-MATERIALIZE-R001` | **Repository-manager materializes an approved proposal into a commit.** Repository-manager alone creates an isolated working copy at the approved base, applies only the approved patch, runs the declared gates, stages the reviewed files explicitly, creates one commit with approved attribution, and submits the result to the existing merge queue rather than reporting it merged directly; it returns an immutable materialization receipt that must be re-ingested before the originating proposal can resolve. Subsystem: governed materialization. Entry: `MaterializationService.materialize` (`repository_manager/materialization/service.py:156`). Caller chain: a planned CLI verb `run_materialize_cli` (`repository_manager/cli_commands/materialization.py`, planned; dispatched beside `run_merge_queue_cli` at `repository_manager/cli_commands/parser.py:781`) and a planned MCP adapter `register_materialization_tools` (`repository_manager/mcp_tools/materialization.py`, planned; added as an entry of `MCP_TOOL_REGISTRY` at `repository_manager/mcp_tools/registry.py:105`) both call `MaterializationService.materialize`, which runs `_check_idempotent_replay` (:206), `_admit` (:220), `_create_worktree` (:237), `_apply_and_commit` (:264) and `_submit` (:292) in that order, then `_finish` (:361). No production module outside `repository_manager/materialization/` calls the service today; the two adapters are the delivery of this row. Shape: types are `ChangeProposal`, `ApprovalProof` and `MaterializationReceipt` in `repository_manager/materialization/models.py`; the three injected ports are `ApprovalAuthority`, `MaterializationReceiptStore` and `MergeQueuePort` in `repository_manager/materialization/ports.py`; the service composes the existing `WorktreeManager` (`repository_manager/worktree.py`), `safe_commit` (`repository_manager/safe_commit.py:613`) and `merge_queue.enqueue` through `GitMergeQueueAdapter` (`ports.py:110`) and adds no second Git-mutating function. Writes: one isolated worktree, one commit on branch `materialize/<proposal_id>`, one queue entry, one receipt through `MaterializationReceiptStore.put`. Depends on: `RM-MATERIALIZE-R002`, `RM-MATERIALIZE-R003`, `RM-MATERIALIZE-R004`, `RM-MATERIALIZE-R005`, `RM-MATERIALIZE-R006`. | Test: `tests/materialization/test_service.py::test_a_passing_gate_commits_with_exactly_the_reviewed_paths` and `tests/materialization/test_service.py::test_queue_acceptance_is_reported_as_queued_never_merged` cover the composed path with a fake Git, fake approval authority and fake queue. The adapter tests `tests/test_materialization_cli.py::test_materialize_verb_returns_the_receipt` and `tests/test_materialization_mcp.py::test_materialize_tool_returns_the_receipt` are planned. |
| `RM-MATERIALIZE-R002` | **Approval verification gates every Git materialization request.** Repository-manager accepts a versioned change proposal carrying its proposal ID, repository ID, exact base commit, approved path allowlist, patch digest, decision identity and expiry, and verifies caller authorization and a signed, verified approval before creating any isolated working copy. Entry: `MaterializationService.materialize` (`service.py:156`). Caller chain: `materialize` calls `_admit` (`service.py:220`) before `_create_worktree`; `_admit` calls the pure `check_binding` (`service.py:74`) for expiry, digest, repository, tenant and actor binding, then `ApprovalAuthority.verify` (`ports.py:77`) for signature authenticity and caller authorization. Shape: `ChangeProposal` (`models.py:113`) is a frozen strict model whose validators reject a malformed ID, a base that is not 40 hex characters, a patch digest that does not match `patch_text`, a patch over `MAX_PATCH_BYTES` and a non-aware `expires_at`; `ChangeProposal.digest` (`models.py:183`) is `canonical_digest` from `repository_manager/development/serialization.py:110`, which `ApprovalProof.proposal_digest` must equal. A binding failure containing `expired` maps to `expired_approval`, every other binding or authority failure to `unauthorized`, and both produce a `refused` receipt before any Git effect. Depends on: `RM-MATERIALIZE-R006`. | Test: `tests/materialization/test_service.py::test_expired_approval_refuses_without_any_worktree`, `tests/materialization/test_service.py::test_approval_bound_to_a_different_proposal_is_unauthorized`, `tests/materialization/test_service.py::test_approval_for_a_different_repository_is_unauthorized`, `tests/materialization/test_service.py::test_approval_from_the_wrong_actor_is_unauthorized`, `tests/materialization/test_service.py::test_approval_authority_rejection_is_unauthorized` and `tests/materialization/test_service.py::test_check_binding_is_pure_and_lists_every_structural_reason`. |
| `RM-MATERIALIZE-R003` | **Patch application is isolated and restricted to approved paths.** Repository-manager resolves the target repository from a portable registry, creates an isolated working copy at the approved base commit, and applies only the approved path allowlist, rejecting path traversal, symlink escapes, unexpected binary content, oversized patches and base drift. Entry: `MaterializationService.materialize` (`service.py:156`). Caller chain: `materialize` calls `_create_worktree` (`service.py:237`), which resolves the repository with `WorktreeManager.resolve_repo`, compares `proposal.base_ref` to `proposal.base_sha` through `_current_ref_sha` (:128) and raises `stale_base` on drift, then calls `WorktreeManager.add` at the approved base; `_apply_and_commit` (:264) calls `apply_patch` (`repository_manager/materialization/patch.py:116`), and a `PatchRejected` becomes `path_rejected` after `_abandon_worktree` (:308) removes the worktree. Shape: `apply_patch` runs `changed_paths_in_patch` (`patch.py:77`) and `_reject_unsafe_paths` (:57) and `_reject_outside_allowlist` (:66) on the header paths, rejects any symlink-mode line with `_SYMLINK_MODE_RE`, then `git apply --check`, re-checks the paths `git apply --numstat` reports through `_numstat_paths` (:93), applies, and re-checks the result with `_reject_symlink_targets` (:109); the size bound is `MAX_PATCH_BYTES` (2 MiB) in `models.py`, enforced when the proposal is built, before any worktree exists. The canonical checkout is read through `run_git` (`patch.py:37`) and never written. Depends on: `RM-MATERIALIZE-R002`. | Test: `tests/materialization/test_service.py::test_valid_patch_touches_only_the_approved_path`, `tests/materialization/test_service.py::test_patch_touching_an_unapproved_path_is_rejected`, `tests/materialization/test_service.py::test_patch_header_with_traversal_is_rejected_statically`, `tests/materialization/test_service.py::test_patch_declaring_a_new_symlink_is_rejected`, `tests/materialization/test_service.py::test_binary_patch_content_is_rejected`, `tests/materialization/test_service.py::test_oversized_patch_is_rejected_before_any_git_mutation_can_start`, `tests/materialization/test_service.py::test_stale_base_is_rejected_before_any_worktree_is_created` and `tests/materialization/test_service.py::test_unknown_repository_is_rejected_as_stale_base`. |
| `RM-MATERIALIZE-R004` | **Validation gates and explicit staging precede every commit.** Repository-manager runs the declared local validation checks against the resulting tree, stages an explicit path list, and creates one commit carrying the approved attribution and exact tree identity. Entry: `MaterializationService.materialize` (`service.py:156`). Caller chain: `materialize` calls `_apply_and_commit` (`service.py:264`), which calls `safe_commit` (`repository_manager/safe_commit.py:613`) with `paths=list(proposal.approved_paths)` and the service's `gate`; a result without `ok` becomes `gate_failed` after `_abandon_worktree`, and `_tree_sha` (:133) records `HEAD^{tree}` of the worktree for the receipt. Shape: the commit message is `materialize <proposal_id> (approved by <decision_identity>)` (`service.py:276`); the gate is the constructor argument `gate` (a command or a callable taking the worktree path), so the declared profile of the proposal (`ChangeProposal.validation_profile`) is recorded on the receipt as `gate_profile` and the caller chooses the gate when it builds the service. Binding `validation_profile` to a named gate set is not built; it needs the gate-profile vocabulary of `repository_manager/validation_policy.py` and is an owner decision. Depends on: `RM-MATERIALIZE-R003`. | Test: `tests/materialization/test_service.py::test_a_failing_gate_blocks_both_commit_and_queue` and `tests/materialization/test_service.py::test_a_passing_gate_commits_with_exactly_the_reviewed_paths`. The profile-to-gate binding test `tests/materialization/test_service.py::test_validation_profile_selects_the_declared_gate` is planned. |
| `RM-MATERIALIZE-R005` | **Merge queue submission never claims landing before verification.** Repository-manager submits the resulting commit to the existing merge queue and reports it as submitted, never as merged, until the queue independently verifies the base, gate results and merge outcome. Entry: `MaterializationService.materialize` (`service.py:156`) and `MaterializationService.reconcile` (`service.py:186`). Caller chain: `materialize` calls `_submit` (`service.py:292`), which calls `MergeQueuePort.submit`; the production adapter `GitMergeQueueAdapter.submit` (`ports.py:119`) calls `merge_queue.enqueue` and never drains the queue. A refusal by the queue becomes `queue_conflict`; an accepted submission yields a `queued` receipt. `reconcile` calls `_reconcile_queued` (`service.py:398`), which calls `GitMergeQueueAdapter.status` (`ports.py:135`); only `merge_queue.LANDED` moves the receipt to `merged`, `merge_queue.REJECTED` moves it to `refused` with `queue_conflict`, and any other state leaves it `queued`. Shape: no code path outside `reconcile` writes `merged`; `reconcile` performs no Git mutation and re-reads the report that `merge-queue-runner.timer` fills. Depends on: `RM-MATERIALIZE-R004`. | Test: `tests/materialization/test_service.py::test_queue_acceptance_is_reported_as_queued_never_merged`, `tests/materialization/test_service.py::test_queue_conflict_is_reported_as_refused_not_success`, `tests/materialization/test_service.py::test_reconcile_promotes_a_landed_candidate_to_merged` and `tests/materialization/test_service.py::test_reconcile_reports_a_rejected_candidate_as_refused`. |
| `RM-MATERIALIZE-R006` | **An immutable receipt binds every materialization outcome.** Repository-manager returns an immutable materialization receipt bound to the proposal, approval, base commit, resulting commit and tree, gate profile and results, merge queue result and an idempotency key, and reconciles uncertain delivery before any retry. Entry: `MaterializationService.materialize` (`service.py:156`). Caller chain: every phase outcome ends in `_finish` (`service.py:361`) or `_pending_receipt` (:378), both calling `_build_receipt` (:328), which builds a `MaterializationReceipt` and stores it through `_persist` (:388) and `MaterializationReceiptStore.put`; a repeated call enters `_check_idempotent_replay` (:206), which returns the stored receipt for the same `proposal_digest` and refuses a different digest under the same key with `unauthorized`. Shape: `MaterializationReceipt` (`models.py:237`) is frozen and strict, carries digests and identities but no patch bytes and no filesystem path, and its validator `_validate_terminal_shape` (`models.py:281`) allows an error code only on `refused` or on `pending` with `uncertain_delivery`; `MaterializationReceipt.digest` uses `canonical_digest`. The gate result digest, the queue result record, the monotonic transition event and the receipt signature of the target design are not fields of the receipt today; adding them is a schema change and an owner decision (see the owner decisions in the pull request). The states `applied`, `validated` and `committed` exist in `MaterializationState` (`models.py:89`) and no code path emits them. Depends on: `RM-MATERIALIZE-R002`, `RM-MATERIALIZE-R005`. | Test: `tests/materialization/test_service.py::test_a_replayed_request_returns_the_same_receipt_without_a_second_commit`, `tests/materialization/test_service.py::test_an_altered_replay_under_the_same_key_is_rejected` and `tests/materialization/test_service.py::test_materialization_receipt_contract_round_trips_through_canonical_serialization`. The receipt-signature and gate-result-digest tests `tests/materialization/test_receipt_contract.py::test_receipt_carries_gate_result_digest_and_signature` are planned. |
| `RM-MATERIALIZE-R007` | **No caller has a direct Git fallback when the service is unavailable.** No caller may bypass repository-manager with a direct Git fallback; when repository-manager, the authorization check, or receipt delivery is unavailable, the request remains pending rather than completing through another path. Entry: `MaterializationService.materialize` (`service.py:156`). Caller chain: `materialize` catches `_UNAVAILABLE_ERRORS` (`service.py:66`: `ApprovalAuthorityUnavailable`, `ReceiptStoreUnavailable`, `MergeQueueUnavailable`, `RepositoryManagerUnavailable`) around all phases and returns `_pending_receipt` (:378), a `pending` receipt with `uncertain_delivery`; `_persist` (:388) logs and still returns the receipt when the store is down; `reconcile` (:186) re-raises `ReceiptStoreUnavailable` and marks a queued receipt pending again when the queue status is unavailable. Shape: the service is the only function in the package that creates a worktree, applies a patch or commits for a proposal; `repository_manager/materialization/__init__.py` exports no other Git-mutating function. Removing direct Git routes from callers is the migration step of the planned adapters of `RM-MATERIALIZE-R001`. Depends on: `RM-MATERIALIZE-R001`. | Test: `tests/materialization/test_service.py::test_unavailable_approval_authority_leaves_the_request_pending`, `tests/materialization/test_service.py::test_unavailable_receipt_store_leaves_the_request_pending` and `tests/materialization/test_service.py::test_unavailable_merge_queue_leaves_a_committed_candidate_pending`. |
