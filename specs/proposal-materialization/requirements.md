# RM-MATERIALIZE-001 requirements

Every requirement this specification owns, with the proof that closes it. Delivery state and
public evidence for each ID are recorded in [`status.json`](status.json); this file defines what
each ID means. The design is in [`spec.md`](spec.md) and [`plan.md`](plan.md), the test contract
in [`test-spec.md`](test-spec.md), and the work order in [`tasks.md`](tasks.md).

| ID | Requirement | Verification |
|---|---|---|
| `RM-MATERIALIZE-R001` | **Repository-manager materializes an approved proposal into a commit.** Repository-manager alone creates an isolated working copy at the approved base, applies only the approved patch, runs the declared gates, stages the reviewed files explicitly, creates one commit with approved attribution, and submits the result to the existing merge queue rather than reporting it merged directly; it returns an immutable materialization receipt that must be re-ingested before the originating proposal can resolve. | Fault-injection and negative tests confirm no Git mutation occurs without a valid caller-verified approval, and a queue rehearsal with a verified receipt confirms the materialization path. |
| `RM-MATERIALIZE-01` | **Approval verification gates every Git materialization request.** Repository-manager accepts a versioned change proposal carrying its proposal ID, repository ID, exact base commit, approved path allowlist, patch digest, decision identity and expiry, and verifies caller authorization and a signed, verified approval before creating any isolated working copy. | Negative tests with missing, expired, altered or wrong-repository approval confirm no Git mutation occurs. |
| `RM-MATERIALIZE-02` | **Patch application is isolated and restricted to approved paths.** Repository-manager resolves the target repository from a portable registry, creates an isolated working copy at the approved base commit, and applies only the approved path allowlist, rejecting path traversal, symlink escapes, unexpected binary content, oversized patches and base drift. | Tests confirm a valid patch touches only allowed paths and each invalid patch leaves the canonical repository unchanged. |
| `RM-MATERIALIZE-03` | **Validation gates and explicit staging precede every commit.** Repository-manager runs the declared local validation checks against the resulting tree, stages an explicit path list, and creates one commit carrying the approved attribution and exact tree identity. | Tests confirm a failed check, a changed tree, or an unreviewed file blocks both the commit and queue admission. |
| `RM-MATERIALIZE-04` | **Merge queue submission never claims landing before verification.** Repository-manager submits the resulting commit to the existing merge queue and reports it as submitted, never as merged, until the queue independently verifies the base, gate results and merge outcome. | Tests confirm a conflicting change or a failing hosted continuous-integration run produces a pending or failed outcome rather than a success report. |
| `RM-MATERIALIZE-05` | **An immutable receipt binds every materialization outcome.** Repository-manager returns an immutable materialization receipt bound to the proposal, approval, base commit, resulting commit and tree, gate profile and results, merge queue result and an idempotency key, and reconciles uncertain delivery before any retry. | Idempotency tests confirm a repeated identical request reconciles to one candidate while an altered replay is rejected. |
| `RM-MATERIALIZE-06` | **No caller has a direct Git fallback when the service is unavailable.** No caller may bypass repository-manager with a direct Git fallback; when repository-manager, the authorization check, or receipt delivery is unavailable, the request remains pending rather than completing through another path. | Fault-injection tests confirm no ungoverned branch or falsely resolved proposal can result from an unavailable dependency. |
